# gelm accessibility

This document records the accessibility decision for stubbedev/gelm#13:
what gelm ships today, why an in-process AT-SPI bridge was deferred
after prototyping it, and what the path to a real screen-reader story
looks like.

## Decision

**gelm does not speak AT-SPI in-process.** Instead it ships:

1. **Semantic roles and state on every widget** — `widget.Role`,
   `widget.Describe`, and `widget.DescribeTree` expose role, name,
   value, text contents with caret and selection, checked state, and
   focusability as a plain Go API with no new dependencies.
2. **A keyboard-first guarantee, pinned by tests** — every interactive
   control in the showcase tree (`cmd/gelm-hello`) is reachable by Tab
   and activatable by Enter or Space, in both the widget unit tests and
   the showcase Tab-order test. This is the accessibility floor for
   toolkits on minimal Wayland setups: even without a screen reader,
   nothing is pointer-only.
3. **A recorded integration path** — see "Alternatives" below for the
   out-of-process bridge design, which keeps gelm's go.mod clean while
   still reaching AT-SPI.

## The prototype, and what it proved

The feasibility question was tested with a real prototype (a few
hundred lines of Go using `github.com/godbus/dbus/v5`, kept out of the
repository), run against **real at-spi2-core 2.60** in a private dbus
session. The mechanics all work:

- Discovering the accessibility bus: call
  `org.a11y.Bus.GetAddress` on the session bus (this dbus-activates
  `at-spi-bus-launcher` via the `org.a11y.Bus.service` file), then
  dial the returned address.
- Registering nothing: recent at-spi2 has **no `RegisterApplication`
  call** (confirmed absent in 2.60). The registry (`org.a11y.atspi.Registry`)
  watches the a11y bus for new unique names and probes
  `/org/a11y/atspi/accessible/root` on each. An application just
  exports objects and idles.
- Serving the tree: `org.a11y.atspi.Accessible`
  (`GetRole`/`GetRoleName`/`GetChildAtIndex`/`GetChildCount`/
  `GetState`/`GetAttributes`), `.Application`, `.Component`,
  `.Action`, `.Text`, plus `org.freedesktop.DBus.Properties` for
  Name/Description. godbus handles all of it; the atspi role and state
  enums are plain uint32 values.
- Consuming it back: a second Go connection played assistive tech,
  walked the tree by bus name, and read roles, states, action names,
  and text with caret offsets. The real registry stayed on the bus
  throughout.

So the wire protocol is **not** the blocker. Pure Go plus godbus is a
viable way to speak AT-SPI, and the numbers above are the whole
registration story on a modern desktop.

## Why the bridge is deferred anyway

- **The gap between "walkable" and "useful" is the expensive part.**
  A tree a client can enumerate needs state *change* signals
  (`StateChanged`, `PropertyChanged`, `CaretMoved`, `ChildrenChanged`,
  text-changed) or a screen reader sees only a snapshot; it needs the
  full surface of the Text interface (19 methods), Value, Selection,
  cached re-validation, and defunct semantics. That is a
  multi-thousand-line subsystem with a permanent dbus/concurrency
  surface, not a small module.
- **Dependency policy.** gelm's go.mod deliberately carries almost
  nothing. godbus is well-behaved (pure Go, one indirect dep), but
  adding it for a bridge that cannot be exercised in this repo's
  gates is exactly the "sprawling half-bridge" trade the project
  declines. `go test ./...` has no dbus daemon, no at-spi2-core, and
  no accerciser to verify against.
- **Environment reality.** gelm targets minimal wlroots setups —
  bars, panels, kiosk apps — where an a11y bus usually is not running
  at all. The bridge would be dead code for most of its users unless
  it also *bootstrapped* the a11y infrastructure, which is a bigger
  and more intrusive commitment.

None of this closes the door. The prototype output above is the
checklist a real bridge would implement first.

## What ships instead

### Semantic roles (`widget/a11y.go`)

- `Role` mirrors the AT-SPI roles an external bridge would translate
  to: button, label, entry, text-area, slider, switch, check-box,
  progress-bar, scroll-area, list, menu, tab-list.
- `Describe(w)` snapshots role, name (tooltip text, else the wrapped
  or own label text), text contents, caret and selection as rune
  offsets, checked state, min/max/value/step, editable, multiline,
  enabled (the effective state, ancestors folded in), focusability,
  and bounds. A read-only text widget reports editable false; a
  disabled one reports enabled, editable, and focusable all false.
- `DescribeTree(root)` walks the tree in paint order — the same order
  focus traversal uses — so an integration can snapshot the whole
  window in one call.

### Keyboard-first guarantee

- `Button` fixes a real bug found by this work: its `KeyAction` had
  the wrong signature, so buttons never implemented `KeyActionHandler`
  and **Tab traversal silently skipped every button**. Buttons now
  activate on Enter and Space (the GTK activation pair).
- `Switch` and `CheckButton` implement `KeyActionHandler` +
  `RuneHandler`: Enter toggles, Space toggles.
- `Slider`, `Entry`, `TextArea`, `List`, `Menu`, and `Notebook` were
  already keyboard-operable; `KeyActionForSym` remains the single
  keysym→action map.
- Pinned by tests:
  - `widget/a11y_test.go` — roles and state snapshots for every
    widget; Enter/Space activation through the router.
  - `cmd/gelm-hello/a11y_test.go` — the Tab-order test over the real
    showcase tree: exactly six focusable controls in paint order
    (button, slider, switch, checkbox, entry, text area), a complete
    one-lap cycle with wrap, shift+Tab backwards, the TextArea Tab
    trap with its ctrl+Tab/shift+Tab escape, and Enter/Space/arrow
    activation of every focused control.

## Alternatives for reaching AT-SPI

**Out-of-process helper (recommended).** A small optional daemon
(`cmd/gelm-a11y`, its own module so gelm's go.mod stays clean) that:

1. reads the accessibility state gelm already exposes — an app opts in
   by serving its `DescribeTree` snapshot (plus a change-feed handle)
   over a private unix socket or shm ring;
2. owns the godbus side: discovers the a11y bus, exports
   Accessible/Component/Text/Action objects, translates snapshots into
   AT-SPI state and events.

Benefits: the dbus dependency lives in the helper, gelm stays
dependency-light, the helper can be tested against a private dbus
session exactly like the prototype, and crash isolation keeps assistive
tech failures out of the app. Cost: a snapshot protocol to design
(widget identity across snapshots, change deltas) and one extra process
per session.

**In-process bridge behind a build tag.** Same godbus work inside a
`//go:build atspi` package, dependency only paid when the tag is set.
Keeps change-signal generation simple (widgets are in-process) but
complicates the module layout and still needs dbus tooling in CI.

**Rely on the compositor.** Wayland has no merged accessibility
protocol yet; existing projects solve narrow cases only. Nothing to
integrate today, but worth re-checking before investing in the helper.

## Revisit triggers

- An AT user or distro asks for Orca/accerciser interop in a real
  deployment with an a11y bus present.
- The out-of-process helper exists and proves the snapshot protocol.
- Wayland grows a compositor-level a11y protocol.
